# F5 BIG-IP - setup for acme

acme works through **iControl REST**:

1. signs in at `/mgmt/shared/authn/login` and uses the token (deleted at the end);
2. uploads the key and certificate (`/mgmt/shared/file-transfer/uploads/`) and installs
   them as `sys crypto key` / `sys crypto cert` `/<partition>/acme-<name>-<date>-<serial>`;
3. installs the chain once as its own certificate `acme-chain-<id>`;
4. in each listed **client-ssl profile** replaces the cert-key-chain entry that held the
   older acme certificate (else `default`, else the first); other entries stay;
5. deletes older acme certificates and keys beyond *keep* (one still used stays);
6. `save sys config`, and with *Sync to device group* `config-sync to-group`.

A dual certificate (ECDSA + RSA) gives each profile two cert-key-chain entries, one of
each kind.

For BIG-IP LTM (TMOS) 13.x and later, hardware, VE and cloud editions.

## What you need

- The BIG-IP's management address (management port or a self IP allowing HTTPS
  management), **TCP 443**, from acme.
- A user who may use iControl REST, manage keys/certificates **and** client-ssl profiles,
  and save the configuration.
- In an HA pair: the device group name for config-sync.

## Set up the BIG-IP

1. Create a local user for acme. The role *Certificate Manager* can manage keys and
   certificates but **not profiles**; for profiles and saving use **Administrator** on
   the partition (or *Resource Administrator*). With `tmsh`:

   ```text
   tmsh create auth user acme password <strong-password> partition-access add { Common { role admin } } shell none
   tmsh save sys config
   ```

   (GUI: **System → Users → User List → Create**, *Role*: Administrator, *Partition
   Access*: the partition, *Terminal Access*: Disabled.)
2. If you restrict management access (**System → Platform → Admin IP / httpd allow
   list**), allow the acme server's address:

   ```text
   tmsh modify sys httpd allow add { 198.51.100.10 }
   ```

3. With remote authentication (LDAP, RADIUS, TACACS+): use its login provider name in
   acme, and map acme's account to the roles above.
4. Note the client-ssl profiles (**Local Traffic → Profiles → SSL → Client**), e.g.
   `/Common/www_clientssl`, and in an HA pair the device group (**Device Management →
   Device Groups**).

## Fill in acme

| acme field | What to put there |
|---|---|
| Address / HTTPS port | The management address, e.g. `bigip.example.local` / `443` |
| User | The user from step 1 (default `acme`) |
| Password | Its password |
| Login provider (advanced) | `tmos` for local users; the remote auth provider's name otherwise |
| Partition | Default `Common` |
| Sync to device group (advanced) | e.g. `dg-failover`; empty: no sync |
| Check the device's certificate / CA certificate | Off only while the BIG-IP has its self-signed certificate |
| Client SSL profiles (deploy) | One a line, e.g. `/Common/www_clientssl` |
| Make missing profiles (deploy, advanced) | A profile not found is made with `clientssl` as its parent |
| Partition (deploy, advanced) | Empty: the target's |
| Previous versions to keep (advanced) | Default 2 |
| Check what is served | The virtual server, e.g. `vip.example.com:443` |

## Check it

- **Try**: `signed in to ..., BIG-IP 17.1.x`.
- On the BIG-IP:

  ```text
  tmsh list sys crypto cert one-line | grep acme-
  tmsh list ltm profile client-ssl www_clientssl cert-key-chain
  tmsh show cm sync-status
  ```

## Common problems

| Problem | Fix |
|---|---|
| 401 on login | Wrong user/password or login provider (`tmos` for local users) |
| 403 / `not authorized` on profiles | The role is Certificate Manager - use Administrator on the partition |
| Profile not found | Give the full path `/Partition/name`, or turn on *Make missing profiles* |
| Older certificate not deleted | Still used by a profile; it goes later |
| Peer unit still has the old certificate | Set *Sync to device group*, check `tmsh show cm sync-status` |
| A profile refuses a second key of the same kind (dual) | Remove the other entry of that kind that is not acme's |
